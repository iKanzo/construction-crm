# Безопасность и ограничения

## Граница доступа

Frontend использует публичный anon key и сессию Supabase Auth. `AuthGate` проверяет наличие сессии и активного профиля, а страница сотрудников перенаправляет пользователей без роли администратора. Эти проверки и скрытие кнопок — удобство интерфейса, не защита API. Защита данных обеспечивается правами PostgreSQL, RLS и проверками внутри RPC и Edge Function; перед использованием их необходимо самостоятельно проверить.

- Локальный API публикует только схему `public`, не `private`. Шести бизнес-таблицам включена RLS; `authenticated` получает SELECT, но не прямую запись. Записывающие действия проходят через RPC с проверкой пользователя и бизнес-правил.
- Активные пользователи видят профили; свой профиль виден и деактивированному пользователю. Видимость объектов и задач зависит от роли и ответственности, чата — от участия в задаче. Администратор и стороны видят соответствующие предложения передачи. Получатель может видеть pending-предложение без доступа к самой задаче; вопрос G15 в [PROJECT_SPEC.md](../PROJECT_SPEC.md) остаётся открытым.
- Ключ `service_role`, пароли и другие секреты нельзя помещать в `VITE_*`, браузерный код или репозиторий. Публичный anon key допустим только при корректных правах и RLS.

## Приглашения

`backend/supabase/functions/invite-user/index.ts` проверяет bearer JWT через Auth и активный профиль администратора; принимает email, имя и роль `manager` или `executor`. Серверный service role key используется для приглашения через Admin API и создания профиля. CORS функции разрешает все источники, поэтому нельзя считать его ограничением доступа. Проверяйте конфигурацию и журналируйте ошибки без раскрытия секретов.

Создание Auth-пользователя и профиля — отдельные операции: при ошибке вставки профиля функция возвращает ошибку и `user_id`, но не удаляет Auth-учётную запись. Администратору потребуется сверить и исправить такое состояние; повторное приглашение не следует считать автоматическим откатом.

## Перед любым развёртыванием

Локальный `seed.sql` содержит известные учётные данные и предназначен только для разработки; не применяйте его в облаке. Локальный `config.toml` не переносит настройки в облачный проект. Отдельно проверьте публичную регистрацию, Auth и redirect URL, доставку почты, секреты Edge Function, доступные схемы, роли, привилегии, RLS, RPC, резервное копирование и восстановление. Локально MFA отключена. Клиентская проверка длины пароля отличается от настроенной в локальном Auth, поэтому окончательные требования обеспечивает сервер.

Тестовые данные не предназначены для production. Наличие тестов, интерфейсных проверок и CI само по себе не подтверждает безопасность или готовность системы к развёртыванию.
