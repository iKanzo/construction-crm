# Разработка и проверки

## Окружение

Используйте Node.js 20+ и npm. Корень — npm workspace с пакетом `frontend`. Установите зависимости командой `npm install`; в проекте нет корневого lock-файла, поэтому версии не зафиксированы. CLI Supabase входит в devDependencies и запускается через npm-скрипты, отдельная глобальная установка не требуется. Для локального стека нужен установленный и запущенный Docker с поддержкой контейнеров Supabase. Если Docker недоступен, команды `db:start`, `db:reset` и Supabase-вариант `test:db` не работают: установите Docker согласно документации вашей ОС или используйте доступный удалённый Supabase только после его отдельной настройки. Без backend можно выполнять frontend-проверки; альтернативу для SQL см. ниже.

```sh
npm run db:start
npm run supabase -- status
```

Скопируйте `.env.example` в `frontend/.env.local`, заполните `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` значениями локального проекта и выполните `npm run dev`. Vite читает окружение из `frontend`; после изменения переменных его нужно перезапустить. Без этих переменных приложение показывает сообщение о конфигурации. Не помещайте секреты в `VITE_*`.

Локальный Auth отключает публичную регистрацию, а seed создаёт демо-пользователей с известным паролем. Значения смотрите в `backend/supabase/seed.sql`; не используйте этот seed вне локального окружения. Почта локального Supabase доступна на `http://127.0.0.1:54324`. Локальный `config.toml` не настраивает облачный проект.

## Edge Function и Auth

Функции нужны серверные `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`; Supabase обычно предоставляет их в окружении Edge Functions. Проверьте их наличие в среде запуска, не записывая service role key в `frontend/.env.local` или `VITE_*`. При отсутствии любого из них функция вернёт `server_configuration`. Локально после запуска стека в отдельном терминале можно обслуживать функцию командой `npm run supabase -- functions serve invite-user`; если среде требуются дополнительные серверные переменные, CLI поддерживает `--env-file` с отдельным незакоммиченным файлом. В облаке отдельно разверните функцию, например `npm run supabase -- functions deploy invite-user --project-ref <project-ref>`, после настройки CLI и доступа к проекту. Эти команды не подтверждают успешную доставку приглашений.

Настройте Auth Site URL и разрешённые redirect URL для реального адреса frontend. Восстановление пароля передаёт `window.location.origin`; приглашение не передаёт явный redirect и использует настройки Auth. Проверьте адреса, шаблоны и доставку писем, локально — в почтовом интерфейсе. Приглашать может только активный администратор; функция проверяет его JWT и профиль. После ошибки создания профиля нужна ручная сверка Auth-пользователя и профиля, автоматического отката нет.

`npm run db:reset` **удаляет данные локальной БД**, повторно применяет миграции и seed. `npm run db:stop` останавливает локальные сервисы. Не выполняйте разрушительные команды против нужных данных.

## Команды проверок

Ниже перечислены доступные команды, а не результаты их выполнения:

```sh
npm run typecheck
npm run lint
npm test
npm run build
npx playwright install chromium
npm run test:e2e
npm run test:db       # при запущенном локальном Supabase
```

Vitest/React Testing Library находятся в `tests/frontend`, Playwright — в `tests/e2e`, pgTAP — в `tests/backend/database`. Playwright запускает отдельный Vite на `127.0.0.1:4173`, не переиспользуя существующий сервер, и задаёт фиктивные публичные Supabase-переменные. Frontend-тесты имитируют Supabase; браузерные smoke-тесты проверяют неавторизованные формы, не реальные бизнес-сценарии. SQL-тесты охватывают структуру, ограничения, триггеры, seed, RLS, привилегии и RPC; они не заменяют сквозную проверку Edge Function и Auth.

Альтернативно `npm run test:db:local` использует PostgreSQL 15+, pgTAP, `psql` и `pg_prove` с Supabase stub вместо настоящих Auth/API. Скрипт **удаляет и создаёт заново** базу `CRM_TEST_DB` (по умолчанию `crm_test`); применяйте только на выделенном тестовом сервере. Подключение задаётся через `PGHOST`, `PGPORT`, `PGUSER` и стандартные переменные libpq.

В `.github/workflows/ci.yml` описаны frontend/e2e и отдельная задача Supabase/pgTAP. Наличие workflow не подтверждает успешный запуск, безопасность или развёртывание. Об архитектуре и ограничениях см. [ARCHITECTURE.md](ARCHITECTURE.md) и [SECURITY.md](SECURITY.md).
