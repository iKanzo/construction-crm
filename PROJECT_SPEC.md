> в переписке. Полный текст ТЗ в файл проекта пока не перенесён. Уточнения ниже имеют
> приоритет в разрешённых противоречиях; остальные бизнес-правила ТЗ не изменяются.

## A. Разрешённые противоречия

| № | Решение |
|---|---|
| C1 | Менеджер имеет доступ к объекту, если он создал объект без задач либо является текущим ответственным хотя бы за одну задачу объекта, независимо от автора задачи и способа назначения. После принятия передачи действует то же общее правило: доступны объект, все его задачи и их история, но не чаты чужих задач. |
| C2 | Администраторов через CRM деактивировать нельзя. Правила 8.3 (не себя, не единственного админа) реализуются как страховочные проверки. Новые админы создаются только вручную в Supabase. |
| C3 | В `transfers.status` добавляется `cancelled`. Предложение отменяется админом (`cancel_transfer`) и автоматически, если задача ушла в `accepted`/`closed` или исполнитель отказался от задачи. |
| C4 | Тестовые пользователи с демо-паролями создаются `seed.sql` только для локальной среды. Пароли для развёрнутого проекта передаются вне репозитория. |
| C5 | К списку RPC из 12.4 добавляются `decline_assignment`, `assign_executor`, `cancel_transfer`. Приглашение — Edge Function `invite-user`. |
| C6 | Текст комментария при возврате на доработку хранится только в `comments` (атомарно с переходом). В истории — `comment_id` без текста. |

## B. Решения по умолчанию

| № | Решение |
|---|---|
| G1 | У `authenticated` нет INSERT/UPDATE/DELETE на таблицы. Запись только через RPC. RLS-политики только SELECT. |
| G2 | Правка названия/описания задачи пишется в историю событием `task_updated` (старое и новое значения). |
| G3 | Чат задач `accepted`/`closed` остаётся открытым. |
| G4 | Прежний исполнитель теряет доступ к переданной задаче. Прежний менеджер теряет доступ к её чату, но может сохранить доступ к задаче и её истории, если имеет доступ к объекту по другой своей задаче. Новый исполнитель и менеджер видят полную историю и чат принятой задачи. |
| G5 | Активные пользователи видят `id`, `full_name`, `role`, `is_active` всех профилей. Email только в своём профиле. |
| G6 | Уведомления только внутри приложения. Чат обновляется polling через TanStack Query, без Realtime. |
| G7 | Страница «Профиль»: имя, роль, email, смена пароля, выход. «Забыли пароль?» входит в авторизацию. |
| G8 | Роль неизменна (триггер). Реактивации нет. |
| G9 | Передача запрещена для задач `accepted`/`closed`. |
| G10 | Приглашение — письмо Supabase (`inviteUserByEmail`). |
| G11 | В список страниц добавляется «Сотрудники» (только админ). |
| G12 | Интерфейс только на русском, без i18n-библиотеки. |
| G13 | Доступ к объекту дают задачи любого статуса. |
| G14 | «Собственные задачи» менеджера — те, где он сейчас `responsible_manager_id`. |

## B2. Уточнение по предложениям передачи

**G15. Получатель передачи до принятия.** Предложение содержит снимок названия задачи,
сохранённый при его создании. Получатель видит этот снимок до принятия предложения, но
само предложение не даёт доступа к задаче, истории, чату или объекту. Доступ по другим
независимым основаниям при этом сохраняется.

## C. Окружение разработки

npm, Node 20+. Для локального Supabase и pgTAP (Этапы 2–6) нужны Docker и Supabase CLI.
Деплой и запуск на данном этапе не рассматриваются.
