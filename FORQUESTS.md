# FORQUESTS — техническая подготовка по Construction CRM

> Внутренний документ разработчика. Это шпаргалка для разбора архитектуры проекта и ответов на технические вопросы. Перед собеседованием полезно не просто прочитать ответы, а открыть соответствующий код и суметь показать, где именно реализовано описанное поведение.

## 1. Краткий рассказ о проекте

**Construction CRM** — веб-приложение для управления строительными объектами, задачами и сотрудниками. Frontend написан на React + TypeScript, backend построен на Supabase: PostgreSQL, Supabase Auth, Row Level Security, SQL-функции (RPC) и Edge Function для приглашения сотрудников.

Это MVP с разделением пользователей на три роли: `admin`, `manager`, `executor`. Важная особенность архитектуры — права доступа проверяются не только в интерфейсе, но и на уровне базы данных через RLS и серверные функции.

Короткий вариант для собеседования:

> Я разработал CRM для строительной компании. В ней есть объекты, задачи, назначения исполнителей, проверка выполнения, передачи задач, история и чат. Клиентская часть — React и TypeScript, серверная логика и данные — Supabase/PostgreSQL. Для разграничения доступа использую RLS и серверные RPC, а для приглашения сотрудников — Edge Function с проверкой администратора. Отдельное внимание уделил сценариям передачи задач и тому, чтобы доступ к объекту не открывал автоматически все задачи внутри него.

Не называй проект крупной корпоративной системой или полностью готовым промышленным продуктом. Корректное позиционирование — реализованный и опубликованный MVP.

## 4. Как запускается приложение

### Корневые команды

```bash
npm install
npm run dev
npm run build
npm run typecheck
npm run lint
npm test
npm run test:e2e
```

### Команды Supabase

```bash
npm run db:start
npm run supabase -- status
npm run db:stop
npm run db:reset
npm run test:db
npm run test:db:local
```

Назначение:
- `db:start` — запускает локальный стек Supabase.
- `supabase -- status` через корневой script — показывает локальные URL и ключи.
- `db:reset` — пересоздаёт локальную БД, применяет миграции и seed. Команда разрушительная для локальных данных.
- `test:db` — запускает SQL-тесты через Supabase CLI.
- `test:db:local` — отдельный Bash harness: создаёт тестовую БД, применяет миграции, seed и запускает `pg_prove`. Требует PostgreSQL, `psql` и `pg_prove`.

### Переменные окружения

Vite запускается из workspace `frontend`, а конфигурация Vite не переопределяет `root` или `envDir`. Поэтому локальный файл с переменными размещается в `frontend/.env.local`.

Нужны:
- `VITE_SUPABASE_URL` — URL Supabase проекта.
- `VITE_SUPABASE_ANON_KEY` — публичный ключ клиента Supabase.

Префикс `VITE_` означает, что переменная доступна клиентскому коду и попадает в клиентскую сборку. Поэтому здесь допустим только публичный ключ. `service_role` / secret key нельзя помещать в `VITE_*`, frontend env или публичный репозиторий.

Файл `.env.example` — шаблон имён переменных, а не рабочий файл с секретами. Реальные значения не коммитятся.

## 5. Архитектура и поток данных

Упрощённая схема:

```text
Пользователь
    |
    v
React UI (React Router)
    |
    +--> TanStack Query: загрузка, кэш, повторные запросы
    |
    v
Supabase JS client
    |
    +--> Supabase Auth: JWT / пользовательская сессия
    |
    +--> PostgREST: чтение данных под RLS
    |
    +--> PostgreSQL RPC: бизнес-операции
    |
    +--> Edge Function invite-user: приглашение сотрудника
                 |
                 v
          Supabase Auth Admin API
          + запись профиля в profiles
```

Frontend отвечает за отображение, формы, маршрутизацию, клиентскую валидацию и удобство работы. Но frontend не является доверенной границей безопасности: запрос можно отправить напрямую, минуя UI.

База данных отвечает за окончательную проверку прав и целостности бизнес-операций. Это позволяет сохранить правила, даже если запрос отправлен вручную или клиентский код изменён.

### Почему часть операций сделана через RPC

Операция вроде «перевести задачу на проверку» может менять не только `tasks.status`, но и создавать запись в `task_history`, добавлять комментарий или отменять связанные передачи. Если выполнить эти действия отдельными клиентскими запросами, часть операций может пройти, а часть — завершиться ошибкой.

PostgreSQL-функция выполняет связанную бизнес-операцию на сервере в рамках транзакционного контекста. Это уменьшает риск частично обновлённого состояния и позволяет централизовать проверку прав.

## 6. Модель данных

Ниже перечислены таблицы, подтверждённые миграциями и SQL-тестами. Для точного перечня всех колонок, ограничений, индексов и внешних ключей открывай актуальные SQL-файлы в `backend/supabase/migrations/`: этот документ не заменяет схему БД.

### `profiles`

Профиль приложения, связанный с пользователем Supabase Auth по `id`.

Подтверждённые поля, используемые кодом и тестами:
- `id` — UUID пользователя;
- `full_name` — имя сотрудника;
- `role` — `admin`, `manager` или `executor`;
- `is_active` — признак активности профиля.

Важное архитектурное решение: роль берётся из `profiles.role`, а не из пользовательских metadata. Это позволяет централизованно управлять ролью в базе.

### `objects`

Строительные объекты. В SQL-тестах используются:
- `id`;
- `title`;
- `address`;
- `customer_name`;
- `customer_phone`;
- `created_by`.

### `tasks`

Рабочие задачи, связанные с объектом:
- `id`;
- `object_id`;
- `title`;
- `created_by`;
- `responsible_manager_id` — менеджер, отвечающий за задачу;
- `assigned_to` — назначенный исполнитель;
- `status`.

Важно различать `responsible_manager_id` и `assigned_to`: это разные виды ответственности и разные основания доступа.

### `transfers`

Предложения о передаче ответственности:
- `id`;
- `task_id`;
- `responsibility_type` — тип передаваемой ответственности (`manager` или `executor`);
- `from_user_id`;
- `to_user_id`;
- `initiated_by`;
- `status`;
- `responded_at`;
- `task_title_snapshot` — сохранённое название задачи на момент предложения.

### `comments`

Сообщения в чате конкретной задачи. В проверках используются `id`, `task_id`, `author_id`, `content`.

### `task_history`

История событий задачи. В проверках используются `id`, `task_id`, `event_type`, `actor_id`, `new_status`, `details`.

### Связи (концептуально)

```text
auth.users
    |
    | 1:1 по id
    v
profiles

profiles --created_by--> objects
objects 1 ---- * tasks

profiles --created_by / responsible_manager_id--> tasks
profiles --assigned_to---------------------------> tasks

tasks 1 ---- * transfers
tasks 1 ---- * comments
tasks 1 ---- * task_history
```

Это концептуальная схема. Точные FK и правила ON DELETE смотри в миграциях.

## 7. Роли и разграничение доступа

В приложении три роли:

| Роль | Основное назначение |
|---|---|
| `admin` | Администрирование и полный обзор |
| `manager` | Управление своими объектами и задачами в рамках ответственности |
| `executor` | Работа с назначенными задачами |

### Главный принцип: доступ к объекту не равен доступу ко всем его задачам

Это один из важнейших моментов проекта.

- Администратор видит все объекты и задачи.
- Менеджер видит объект, если он его создал или отвечает хотя бы за одну задачу этого объекта.
- Но полную строку задачи менеджер видит только тогда, когда `responsible_manager_id = auth.uid()`.
- Исполнитель видит объект в контексте назначенной ему задачи.
- Полную строку задачи исполнитель видит только при `assigned_to = auth.uid()`.
- Неактивный профиль не должен получать рабочий доступ.
- Пользователь без активного профиля не получает доступ к данным приложения.

Менеджер может иметь обзор объекта и ограниченную сводку задач, не получая полные описания, статусы, историю и чат чужих задач.

### Почему это важно

Если менеджер отвечает за одну задачу на объекте, это не означает, что ему нужно видеть все остальные задачи этого объекта. Разделение объектного и task-level доступа уменьшает избыточное раскрытие данных.

### Основные helper-функции в схеме

В подтверждённой миграции используются функции схемы `private`:
- `private.auth_role()` — определяет роль текущего пользователя;
- `private.require_active_profile(...)` — проверяет активный профиль и требуемую роль;
- `private.manager_has_object_access(...)` — проверяет основание доступа менеджера к объекту;
- `private.manager_object_ids()` — список объектов, доступных менеджеру;
- `private.visible_object_ids()` — набор видимых объектов с учётом роли;
- `private.can_view_object(...)` — проверка доступа к объекту;
- `private.can_view_task_row(...)` / `private.can_view_task(...)` — проверка доступа к строке задачи;
- `private.can_view_chat(...)` — проверка доступа к чату задачи.

В миграции функции ограничены по EXECUTE: доступ не должен выдаваться `anon` и `PUBLIC`; разрешения выдаются нужной роли `authenticated`.

### RLS

RLS (Row Level Security) — механизм PostgreSQL, который фильтрует строки в зависимости от текущего пользователя и политики.

В проекте RLS используется для таблиц с рабочими данными. Это означает, что запрос вида `select * from tasks` не должен возвращать пользователю все строки: база применяет политику к каждой строке.

Фраза для собеседования:

> Проверки в интерфейсе нужны для UX, но они не защищают данные. Реальную границу доступа задают RLS policies и серверные функции, которые опираются на auth.uid() и активный профиль.

Не говори, что «скрытая кнопка защищает операцию». Скрытая кнопка лишь убирает недоступное действие из интерфейса; запрет должен существовать и на backend.

## 8. Бизнес-операции и RPC

По SQL-регрессионным тестам в проекте используются следующие RPC (полный список и сигнатуры сверяй по миграциям):

| RPC | Назначение |
|---|---|
| `create_object` | Создание объекта |
| `update_object` | Изменение объекта с проверкой прав и состояния задач |
| `delete_object` | Удаление объекта при соблюдении ограничений |
| `create_task` | Создание задачи |
| `assign_executor` | Назначение исполнителя |
| `decline_assignment` | Отказ от назначения |
| `update_task` | Изменение данных задачи |
| `transition_task` | Изменение состояния задачи по бизнес-правилам |
| `create_transfer` | Создание предложения о передаче ответственности |
| `respond_to_transfer` | Принятие или отклонение предложения |
| `cancel_transfer` | Отмена предложения |
| `deactivate_user` | Деактивация сотрудника |
| `add_comment` | Добавление сообщения |
| `get_task_object_title` | Получение названия объекта для доступной задачи |
| `get_object_task_summaries` | Ограниченная сводка задач объекта |

### Изменение статуса задачи

В тестах явно проверяются состояния `under_review`, `revision`, `accepted`, `closed`.

Подтверждённые правила:
- исполнитель может отправить задачу на проверку (`under_review`);
- нельзя принять задачу до прохождения проверки;
- возврат на доработку (`revision`) требует непустого комментария;
- текст комментария хранится в `comments`, а запись истории ссылается на него через `details.comment_id`, не копируя текст повторно;
- изменение статуса проверяется серверной функцией, а не только интерфейсом.

Не перечисляй эти четыре значения как полный enum, пока не сверил все миграции.

### Ограничения объектов

Подтверждено в миграции:
- менеджер может изменить объект только если он его создатель;
- изменение объекта блокируется, если у него есть незавершённые задачи (статусы, отличные от `accepted` и `closed`);
- удалить объект можно только при отсутствии связанных задач;
- операции используют блокировку строки объекта `FOR UPDATE`.

Это защищает от удаления или редактирования объекта в неподходящий момент.

### Деактивация сотрудника

Проверки подтверждают:
- нельзя деактивировать администратора;
- нельзя деактивировать исполнителя, у которого есть открытая задача;
- обычный исполнитель не может деактивировать другого пользователя.

## 9. Передача ответственности — важный сценарий

Передача не должна сразу открывать данные получателю. Она проходит через предложение и ответ получателя.

### Последовательность

1. Уполномоченный пользователь вызывает `create_transfer`.
2. В `transfers` создаётся предложение с типом ответственности, отправителем, получателем и задачей.
3. Получатель может увидеть предложение и сохранённое название задачи.
4. До принятия предложения получатель не видит полную задачу, объект, историю или чат только на основании самого предложения.
5. После принятия меняется текущая ответственность.
6. После принятия доступ появляется в рамках переданной задачи, а не автоматически ко всем задачам объекта.

### Снимок названия задачи

Миграция `20261105000800_manager_access_transfer_snapshot.sql` добавляет `task_title_snapshot`.

Почему snapshot нужен:
- название задачи может измениться после создания предложения;
- получателю и в истории передачи важно видеть исходное название;
- значение записывает серверный trigger `trg_05_snapshot_title`, а не доверяет клиенту;
- отдельный trigger `trg_11_immutable_snapshot` запрещает менять сохранённый снимок;
- при вставке сервер перезаписывает присланное клиентом значение актуальным названием задачи.

Для старых записей миграция заполняет snapshot текущим названием на момент применения миграции. Историческое название для старых предложений восстановить невозможно.

### Конкурентные изменения

В бизнес-операциях передачи и назначения используются блокировки строк и проверки текущего состояния. Это важно, если два пользователя почти одновременно пытаются изменить ответственность или состояние одной задачи: операция должна проверять актуальные данные, а не полагаться на состояние, которое frontend загрузил несколько секунд назад.

## 10. Приглашение сотрудника: Edge Function

Файл: `backend/supabase/functions/invite-user/index.ts`.

Функция `invite-user` выполняет серверное приглашение. Ключевые шаги:

1. Обрабатывает CORS preflight `OPTIONS`; принимает только `POST`.
2. Проверяет наличие серверных переменных `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.
3. Проверяет Bearer token в заголовке Authorization.
4. Создаёт Supabase client с JWT вызывающего пользователя и вызывает `auth.getUser()`.
5. Читает профиль из `profiles` и проверяет `role = admin` и `is_active = true`.
6. Валидирует email, full_name и роль. Приглашать можно только `manager` или `executor`.
7. Создаёт приглашение через `auth.admin.inviteUserByEmail()`.
8. Добавляет профиль в `profiles`.
9. Возвращает `201` и user_id только если обе операции завершились успешно.

### Почему service role находится только в Edge Function

Service role имеет привилегии, позволяющие обходить RLS. Если положить этот ключ в браузерный код, любой пользователь сможет извлечь его из сборки и выполнять запросы с повышенными правами.

Поэтому:
- frontend использует только публичный anon/publishable key;
- service role доступен только серверной Edge Function;
- Edge Function сначала проверяет JWT и активную роль администратора, и только затем использует Admin API.

### Важный нюанс: две системы хранения

Создание пользователя в Supabase Auth и вставка строки в `profiles` — два отдельных обращения. Они не являются одной общей транзакцией PostgreSQL.

В коде предусмотрено: если Auth-приглашение создано, но вставка профиля не удалась, функция возвращает `500 profile_creation_failed`, пишет техническую ошибку в лог и не удаляет потенциально существующую учётную запись автоматически. Такой случай требует ручной сверки администратором.

Это хороший пример честного ответа о trade-off: распределённая операция между Auth Admin API и таблицей приложения не атомарна.

## 11. Frontend: управление состоянием

- React Router отвечает за навигацию.

Данные объектов и задач приходят с backend, поэтому их кэш и повторная загрузка относятся к TanStack Query. Локальные UI-состояния — например, открытие диалога или значение временного поля — не нужно автоматически переносить в глобальный серверный кэш.

При изменении данных важно инвалидировать или обновлять соответствующие query cache entries, чтобы UI не показывал устаревшее состояние.

В `backend/supabase/config.toml` Realtime отключён. Комментарий к конфигурации указывает, что чат работает через polling TanStack Query. Это сознательный компромисс MVP: проще инфраструктура и меньше движущихся частей, но сообщения не доставляются через постоянное realtime-соединение и могут появляться с задержкой интервала опроса.

Storage также отключён: файлы в текущем MVP не используются.

## 15. Безопасность: что важно объяснить

1. **JWT удостоверяет пользователя.** Supabase Auth выдаёт сессию; запросы выполняются от имени пользователя.
2. **auth.uid() — источник идентификатора пользователя на стороне PostgreSQL.** Нельзя доверять user_id, который клиент прислал как обычный параметр, если операция должна выполняться от текущего пользователя.
3. **Роль берётся из profiles.** В проекте роль приложения хранится в таблице профилей.
4. **RLS ограничивает строки.** Пользователь не должен получить чужие записи простым прямым запросом.
5. **RPC проверяет бизнес-правила.** Важные операции централизованы в PostgreSQL.
6. **SECURITY DEFINER требует особой осторожности.** Такая функция исполняется с правами владельца. Нужно проверять вызывающего пользователя внутри функции, использовать безопасный `search_path`, ограничивать EXECUTE и не доверять произвольным параметрам клиента.
7. **Service role — только сервер.** Никогда не отправлять его в браузер.
8. **Валидация есть на нескольких уровнях.** UI-валидация удобна пользователю; backend validation и ограничения БД защищают данные.
9. **Неактивный профиль не должен работать.** Проверка активного профиля выполняется в серверной логике доступа.
10. **Публичная регистрация выключена в локальной конфигурации.** Сотрудников приглашает администратор через Edge Function.

## 16. Вопросы с собеседования и ответы

### Почему выбрал Supabase, а не писал отдельный backend на Express/Nest?

Для MVP Supabase дал готовые PostgreSQL, Auth, API и Edge Functions. Это позволило сосредоточиться на модели данных, правах и бизнес-операциях, не создавая отдельный сервер только ради CRUD. При этом сложная логика не размазана по клиенту: критические операции выполняются SQL RPC, а доступ к данным ограничен RLS.

Trade-off: сильная зависимость от платформы и необходимость хорошо понимать PostgreSQL, RLS и особенности Supabase. Если проект вырастет в сложную интеграционную систему, может понадобиться отдельный backend или дополнительные сервисы.

### Что такое RLS и зачем он здесь?

Row Level Security — механизм PostgreSQL, который определяет, какие строки текущая роль БД может читать или изменять. Он нужен, чтобы пользователь не мог получить чужие задачи прямым запросом, обходя React-интерфейс.

### Чем RLS отличается от проверки роли в React?

React-проверка управляет отображением интерфейса. Её можно обойти. RLS выполняется на стороне БД и ограничивает сами данные. Поэтому frontend — не security boundary.

### Зачем разделены доступ к объекту и доступ к задаче?

Объект может быть общим контекстом для нескольких менеджеров, но каждый менеджер отвечает за отдельные задачи. Если разрешить видеть все задачи по факту доступа к объекту, сотрудник получит лишние данные. Поэтому есть отдельная проверка видимости объекта, полной строки задачи, истории и чата.

### Почему RPC, а не несколько запросов из frontend?

Одна бизнес-операция может затрагивать несколько таблиц. Серверная функция позволяет выполнить связанные изменения последовательно и транзакционно, централизовать проверки и не зависеть от клиентского порядка запросов.

### Что делает SECURITY DEFINER и в чём риск?

Функция выполняется с правами владельца, а не вызывающего пользователя. Это полезно, когда для безопасного сценария нужно прочитать строки, скрытые RLS, но повышает требования к реализации. Функция должна сама проверить `auth.uid()`, роль, активность профиля и право на конкретную операцию. Также нужно задавать безопасный `search_path` и явно управлять EXECUTE privileges.

### Зачем snapshot названия в transfers?

Предложение о передаче должно сохранять контекст на момент создания. Если задачу переименовали, старое предложение не должно менять своё отображаемое название. Snapshot записывается триггером на сервере и защищён от последующего UPDATE.

### Почему получатель не видит задачу до принятия передачи?

Сам факт предложения ещё не означает, что получатель согласился принять ответственность. До принятия ему достаточно увидеть информацию о предложении. Полный доступ появляется после принятия и только к переданной задаче. Это разделяет уведомление/предложение и фактическую передачу прав.

### Как защищаетесь от гонок при одновременных изменениях?

Критические операции повторно проверяют актуальное состояние на backend и используют блокировки строк (например, `FOR UPDATE`). Нельзя полагаться только на состояние, которое frontend загрузил ранее: оно могло устареть. В тестах проверяются конфликтные бизнес-сценарии и некорректные переходы.

### Что такое транзакция?

Транзакция объединяет несколько SQL-операций в одну логическую единицу. При успехе изменения фиксируются вместе, при ошибке транзакция откатывается. Это важно, когда изменение задачи должно сопровождаться записью истории или обработкой связанных передач.

### Что такое TanStack Query и зачем он нужен?

Это библиотека для серверного состояния: загрузка данных, кэширование, состояния loading/error, повторные запросы и инвалидирование кэша после мутаций. Она не заменяет PostgreSQL и не должна использоваться как источник истины для прав доступа.

### Почему чат не на Supabase Realtime?

В текущем MVP используется polling через TanStack Query; Realtime выключен в локальной конфигурации. Это проще для первой версии, но уступает push-событиям по мгновенности и эффективности при большом количестве пользователей.

### Как работает приглашение пользователя?

Edge Function получает JWT, проверяет его через Auth, загружает профиль и убеждается, что пользователь — активный администратор. Затем валидирует данные, вызывает Auth Admin API для приглашения и создаёт запись профиля. Service role хранится только на сервере.

### Есть ли атомарность между созданием Auth user и профиля?

Нет, это отдельные вызовы к Auth Admin API и Postgres. Если Auth-приглашение прошло, а профиль не создался, функция возвращает ошибку и оставляет запись для ручной сверки. Автоматически удалять Auth user опасно: можно затронуть уже существующую учётную запись.

### Что тестируется?

Frontend-тесты проверяют компоненты и пользовательское поведение. SQL/pgTAP тесты проверяют RLS, матрицу видимости, бизнес-RPC, передачи и snapshot. Playwright предназначен для сквозных браузерных сценариев. Разные уровни тестов ловят разные классы ошибок.

### Почему не хранить всю бизнес-логику в React?

Клиент недоверенный и может быть изменён. Если правила существуют только в UI, их можно обойти прямым HTTP-запросом. Серверная логика обеспечивает одинаковое поведение независимо от клиента.

### Что бы ты улучшил дальше?

Отвечай в контексте реальных приоритетов, а не обещай переписать всё:
- расширить E2E на критические end-to-end сценарии ролей;
- следить за актуальным CI и стабильностью SQL-тестов;
- добавить наблюдаемость ошибок Edge Functions и backend-операций;
- продумать резервное копирование и регламент восстановления cloud Supabase;
- пересмотреть необходимость Realtime, если polling станет недостаточным;
- добавить MFA и более строгие настройки Auth, если этого потребуют риски и пользователи;
- расширять тесты конкурентного выполнения и сложных передач.
